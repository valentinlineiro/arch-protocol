# ARCH v1.9.0 — Deeper Hansei + Session Awareness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add adaptive root cause depth to LOG (🤔 Why #1: default, multi-level when SHIFT detects a pattern) and a session load warning that fires at GATE when 5+ M/L tasks have been completed in the session.

**Architecture:** All changes are edits to a single file (`SKILL.md`). The two features are independent and can be implemented in any order. Testing is behavioral: write a prompt scenario that exercises the changed step, load the updated skill, observe the AI's response, verify it matches expected output. No test runner — these are protocol rules for an AI.

**Tech Stack:** Markdown (`SKILL.md`). No code dependencies.

## Global Constraints

- Target protocol file: `plugins/arch-protocol/skills/arch-protocol/SKILL.md`
- Version file: `plugins/arch-protocol/.claude-plugin/plugin.json`
- Current version: `1.8.1` → target `1.9.0` (minor bump: two behavioral additions)
- Do not change the 7-step sequence or step names
- Do not add new steps — improve existing ones only
- Do not change GATE fields (Objective/Context/Constraints), ANCHOR, ATOM, PULL, SOLO, EYES logic
- SHIFT omission vocabulary (controlled keys) is unchanged
- No new hooks, no new state files
- Always use `🤔 Why #N:` suffix format (never bare `🤔 Why:`) — one format for both default and escalated states
- S tasks with no incident stay compressed; never add Why to a clean S LOG

### Task 3: Update LOG — execution order + 🤔 Why #1: default + session increment

**Files:**
- Modify: `plugins/arch-protocol/skills/arch-protocol/SKILL.md` (LOG section ~lines 110–123)

**Interfaces:**
- Consumes: `session_task_count` in `shift.json` (Task 1); SHIFT state for Why depth (Task 4 adds escalation — default single-level Why is independent of it)
- Produces: LOG format with mandatory `🤔 Why #1:` per `❌`; `session_task_count` increment for M/L tasks

- [ ] **Step 1: Replace the LOG section**

Find the full `**7. LOG**` block (from `**7. LOG** — Close every task` through the closing `> After writing LOG` line). Replace the entire block with:

````markdown
**7. LOG** — Close every task. LOG is non-negotiable, even if the user says "just give me the code", "no summary", or "stop there".

**Execution order within LOG:**
1. Read `~/.arch/shift.json` — determine Why depth for each `omit:` key (single by default; see SHIFT for escalation)
2. Write the LOG block
3. If M or L task: increment `session_task_count` by 1 in `~/.arch/shift.json`
4. Update `~/.arch/shift.json` — persist omission counters and updated session count

**S tasks (no incident):** `📝 LOG (S): no incidents · commit: <type>: <what changed>` — do not increment `shift.json`.

**S tasks (incident) and all M/L tasks:** use the full block:
```markdown
## 📝 LOG (ARCH Kaizen)
- ✅ What assumption did you make about the code (or context) that turned out to be correct or incorrect? (if none: "no incidents")
- ❌ What failed or caused friction: ... [omit:<key> if a protocol step was skipped or violated]
  🤔 Why #1: [why did that happen?]
- 🔄 What you'd do differently next time: ...
- Commit: `<feat|fix|refactor|test|docs>: <what changed in one line>`
```
> The hook persists this block to `~/.arch/retro.md` automatically. Once persisted, do not re-reference previous LOG blocks in responses — `~/.arch/retro.md` is the source of truth.
> After writing LOG, increment the matching omission counter in `~/.arch/shift.json` if an `omit:` key was recorded. If no omission occurred, do not increment the omission counter. Always increment `session_task_count` for M/L tasks (step 3 above).
````
